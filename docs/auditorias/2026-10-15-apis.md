## Classificação e inventário

O frontend usa Electron IPC, não API REST. `backend/aplicativo/preload.cjs` expõe `window.prumo`, com funções fechadas que chamam `ipcRenderer.invoke('prumo:'+canal,args)`. `backend/aplicativo/api/registrarCanaisIpc.ts` liga cada canal a `backend/<tela>/api/`. O catálogo de schemas está em `catalogoDeContratos.ts`. `registrarCanal.ts:17` registra `ipcMain.handle`, verifica janela/mainFrame/origem, valida Zod, aplica RBAC e devolve `{ok:true,data}` ou `{ok:false,error}`. O inventário completo canal → handler segue abaixo.

`backend/mcp.ts` usa `StdioServerTransport`: MCP por stdio, não HTTP. As oito ferramentas são `contexto_projeto`, `revisar_cobertura`, `executar_validacao`, `consultar_evidencias`, `listar_politicas`, `propor_caso`, `propor_bug`, `propor_aprendizado`. Cada uma tem `registrar<Nome>.ts` em `backend/agentes/mcp/`. Roteiros são prompts, não ferramentas adicionais. `criarServidor.ts` fixa a raiz na inicialização e aplica política por capacidade a cada chamada. Propostas ficam RASCUNHO; não publicam diretamente em Jira/Qase. Execução exige contrato e aprovação nativa. A identidade declarada no handshake não autentica pessoa. MCP não herda RBAC/sessão da janela; isso é diferença de fronteira, não prova isolada de bypass.

Há HTTP real no OAuth: `backend/login/regras/entradaPorProvedor.ts:105` cria servidor em `127.0.0.1:porta-efêmera`, exclusivamente `GET /callback`. Valida Host, state aleatório e caminho, usa PKCE S256 e timeout de 5 min. Não é servidor web das telas.

## API-01 — confirmação incompleta das edições

**Confirmado; prioridade alta.** `backend/testes/integracoes/editarCasoNoQase.ts:18` retorna true sem GET quando título não foi enviado; com título, compara somente title. `backend/tickets/integracoes/editarTicket.ts:20` relê apenas summary e retorna true para edição sem resumo. `backend/conexoes/escrita/executarOperacaoUmaVez.ts:46` usa esse boolean; linha 49 persiste CONFIRMADA e linha 36 reutiliza uma operação já confirmada.

Impacto: descrição, passos, pré-condições, prioridade, automação ou rótulos podem ser apresentados como confirmados sem verificação do efeito. Não significa que todas essas escritas falham. Divergência/rejeição parcial do serviço pode passar despercebida e nova solicitação apenas reutilizar a confirmação incorreta.

Causa: confirmação restrita a título/resumo. Recomendação: reler e comparar todos os campos solicitados; confirmação parcial mantém ENVIADA e aviso. Teste recomendado: double aceita escrita e preserva campos antigos; verificar false para cada campo divergente e edição mista. Os testes existentes de edição conferem o caminho positivo com título/resumo.

Reprodução executada em módulos `dist/` existentes, com fontes conferidas e contexto sintético, sem rede/banco. Comando PowerShell exato:

```powershell
@'
import { editarCasoNoQase as q } from './dist/testes/integracoes/editarCasoNoQase.js';
import { editarTicket as j } from './dist/tickets/integracoes/editarTicket.js';
let leituras=0;
const ctx={ler:async()=>{leituras++;return {fields:{summary:'inalterado'}}}};
console.log(JSON.stringify({qase:await q.confirmar(ctx,{chave:'LAB'},{casoId:1,descricao:'novo'}),leiturasQase:leituras}));
console.log(JSON.stringify({jira:await j.confirmar(ctx,{chave:'LAB'},{ticket:'LAB-1',descricao:'novo'}),leiturasTotais:leituras}));
'@ | node --input-type=module
```

Saída, exit 0:

```json
{"qase":true,"leiturasQase":0}
{"jira":true,"leiturasTotais":1}
```

Uma primeira invocação equivalente por `node -e` falhou por escape de aspas no PowerShell (SyntaxError); o comando acima corrigiu a invocação. A reprodução pontual não equivale a PASS de suíte.

## API-02 — retenção da razão limita a idempotência

**Provável; prioridade média.** `backend/conexoes/banco/gravarRegistroDeOperacoes.ts:5` conserva somente 1.500 operações. `executarOperacaoUmaVez.ts:44` só chama reconciliar se existe `anterior`. `backend/tickets/integracoes/criarTicket.ts:17` cria sem buscar previamente marcador; a busca está no reconciliador.

Reprodução proposta: criar ticket A, acumular mais de 1.500 chaves distintas, repetir A após descarte da razão local. Sem anterior, a busca de reconciliação é pulada e existe caminho para novo POST com o mesmo marcador. Não reproduzido com persistência nem remoto. Impacto provável: duplicação após retenção apesar da promessa ampla de idempotência.

Recomendação: reconciliar antes de criar mesmo sem registro ou preservar tombstones e declarar horizonte. Teste recomendado inteiramente em memória: razão sem A e remoto contendo marcador A devem reutilizar, nunca criar segundo ticket.

## API-03 — busca incompleta pode provocar reenvio na reconciliação

**Provável; prioridade média.** `backend/testes/integracoes/resultadosDaRun.ts:10` limita busca aos offsets 0..900, sem sinal de completude. `publicarResultadosNoQase.ts` decide faltantes com esse array. `listarNoQase.ts:8` lê só uma página, utilizada por `criarRunNoQaseOperacao.ts` no reconciliador.

Reprodução proposta: marcador além dos primeiros 1.000 resultados ou além da primeira página da busca de runs; perder resposta e repetir solicitação. A busca pode concluir ausência e reenviar. Ordenação/limites reais não verificados, portanto duplicação remota permanece provável. Recomendação: paginar até conclusão comprovada; teto deve bloquear reenvio com estado incompleto. Teste recomendado: fixture em memória com marcador só na página posterior ao teto, garantindo ausência de novo POST.
